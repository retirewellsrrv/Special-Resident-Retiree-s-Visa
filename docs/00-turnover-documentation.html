2. Technical & System Documentation

Architecture, technology stack, project structure, and the design decisions behind the SRRV Service Platform.

Architecture Overview

The SRRV Service Platform is a single Next.js application (no separate backend service). It serves three audiences from one codebase:

  • Public site — informational pages, no auth required.
  • Applicant portal (/applicant/*) — signed-in retirees managing their SRRV application.
  • Admin portal (/admin/*) — staff reviewing consultations, applications, documents, payments.
  • Super Admin portal (/super-admin/*) — manages admin accounts, read-only client register.

Key Design Decisions / Patterns

  • Server Actions over REST for app logic. Only 3 real HTTP route handlers exist (see §6); everything else the UI needs — creating an application, reviewing a document, managing admins — is a Server Action in src/actions/, called directly from Server/Client Components. Naming convention: xAction (e.g. loginAction).
  • Role is derived server-side from the database, not trusted from the JWT alone. A user's role (applicant / admin / super_admin) is resolved by checking super_admin_profiles then admin_profiles.is_active in src/utils/auth/getUser.ts — the same logic is duplicated in middleware.ts and the auth callback route, since user_metadata.role on the Supabase session can be stale or spoofed client-side.
  • Three tiers of authorization enforcement:
    1. Middleware (src/lib/supabase/middleware.ts) — redirects users away from route prefixes (/applicant, /admin, /super-admin) their role doesn't match.
    2. Page/layout guards — assertRole() redirects to /unauthorized.
    3. Server Action guards — requireAdmin() / requireSuperAdmin() / requireApplicant() / withAdmin() / withSuperAdmin() return a typed { authorized: false, error } result instead of throwing, so actions can surface a proper error to the UI.
  • Zod validation at the Server Action boundary. Schemas live in src/schemas/, validated with .safeParse() inside the action before touching the database.
  • revalidatePath before redirect is a documented convention (AGENTS.md) — since redirect() throws, any cache revalidation must happen first or it's skipped.
  • Two Supabase clients: a request-scoped client (createClient, publishable key + user cookies, subject to RLS) and an admin client (createAdminClient, service-role key, bypasses RLS) used only in trusted server contexts (webhooks, role lookups, admin actions).
  • Payment status is intended to be provider-authoritative. payments.status is only ever written by the Xendit webhook handler in application code — the admin UI can only read payment state.
    Caveat. This is an application-layer convention, not a database-enforced one — the live RLS policy on payments actually lets an authenticated user update their own payment row directly. See §5 and §12.
  • One active payment per user+service. A partial unique index guarantees a user can't have two simultaneous pending/success payments for the same service, and the webhook handler has an explicit dedup guard against double-counting a paid invoice.

3. Deployment Guide

Hosting, build commands, deployment steps, rollback procedure, and domain/DNS configuration.

Hosting Provider

Vercel. The app is a standard Next.js project with no vercel.json overrides — Vercel's default Next.js build/runtime detection applies.

To verify. Confirm in the Vercel dashboard (Project → Settings) whether the branch → environment mapping described below is actually configured that way. This guide was written without live Vercel access at the time — the CLI was logged out, and login is an interactive browser step that has to be done by whoever holds the account.

Build Commands

pnpm install --frozen-lockfile
pnpm build       # runs `next build`

Local dev: pnpm dev. Production start (only relevant for non-Vercel runs): pnpm start.

The pnpm build step needs these environment variables available at build time (see §4 for the full list and purpose): NEXT_PUBLIC_SUPABASE_URL, NEXT_PUBLIC_SUPABASE_ANON_KEY, NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY, SUPABASE_SECRET_KEY, XENDIT_SECRET_KEY, XENDIT_WEBHOOK_TOKEN — these must be set as Vercel Project → Environment Variables for each environment (Production / Preview / Development), the same way they're set as GitHub Actions secrets for CI.

Deployment Steps

Branch flow (confirmed by the team): every change is promoted through three branches via PR —

feature/* → PR → develop  (dev/QA)
develop   → PR → staging  (live testing)
staging   → PR → main     (production)

.github/workflows/promote-staging.yml provides a manual workflow_dispatch job that opens the develop → staging promotion PR automatically (gh pr create) — run it from the Actions tab rather than opening that PR by hand.

CI (.github/workflows/ci.yml) runs on every PR into develop, staging, or main: pnpm install --frozen-lockfile → pnpm tsc --noEmit → pnpm test:coverage → pnpm build. This is a gate, not a deploy — it does not push anything live.

Deploys to Vercel are not wired into GitHub Actions. .github/workflows/deploy-production.yml exists but is entirely commented out. In practice, deploys almost certainly happen through Vercel's own native GitHub integration — Vercel watches the connected repo directly and builds/deploys on push, independent of the Actions workflows above. Confirm this in Vercel Project → Settings → Git, and note there which branches map to which Vercel environment (typically main → Production, other branches → Preview deployments).

Manual fallback, if ever needed and the CLI is authenticated:

vercel login
vercel link            # first time only, links this repo to the Vercel project
vercel deploy --prod   # deploy the current branch to Production

Rollback Procedure

Vercel keeps every deployment immutable and browsable. To roll back:

  1. Vercel dashboard → Project → Deployments.
  2. Find the last known-good deployment (by commit/branch).
  3. Click ⋯ → Promote to Production (Vercel's "Instant Rollback") — this repoints the production domain to that build with no rebuild required.
  4. Alternatively via CLI: vercel rollback [deployment-url].

No database rollback tooling exists in this project — a Vercel rollback only affects application code, not Supabase schema/data. See §5 for schema history and §10 for backup/restore.

Row Level Security — Pattern and Exceptions

Most tables (applications, consultations, contacts, dependents, documents, educations, emergency_contacts, employments, family_backgrounds, passports, visa_details, client_profiles) follow the same RLS pattern: owner (user_id/via their application) OR any row in admin_profiles OR any row in super_admin_profiles can select/insert/update/delete. notifications and admin_notifications are scoped strictly to their own user_id/admin_user_id. admin_profiles, super_admin_profiles, and email_logs have RLS enabled with no or near-no policies — access goes through the service-role admin client only.

Two things worth flagging (also listed in §12):
  1. payments RLS allows an authenticated user to INSERT/UPDATE/SELECT their own payment row directly — no restriction on which columns or values. The application's own Server Actions/webhook never let a user set their own payment to success, but RLS doesn't stop a client from calling the Supabase REST/JS API directly to do exactly that.
  2. The "is admin" RLS check doesn't look at admin_profiles.is_active. The app's own authorization treats a disabled admin as a plain applicant, but the RLS policies only check row existence in admin_profiles, not is_active. A disabled admin who retains a valid session could still read/write anything the "any admin" RLS branch allows.
Neither of these was caught by application-level testing since the app never issues the requests that would exploit them — they only show up by reading the RLS policy definitions directly.

6. API Documentation

The application's HTTP endpoints and Server Actions.

This app is a Next.js App Router application. Its real "API" surface for the UI is almost entirely Server Actions (src/actions/), not REST endpoints — these are called directly from React components over Next.js's internal RPC mechanism, not fetch, and have no URL, method, or public contract in the traditional sense. Only 3 genuine HTTP route handlers exist under src/app/api/. Both are documented below; a companion OpenAPI file (06-api-collection.json) covers just those 3 routes, since that's what OpenAPI/Postman are meant to describe.

REST Endpoints

GET /api/auth/callback

File: src/app/api/auth/callback/route.ts
Purpose: Supabase Auth callback — completes an OAuth login (?code=) or an email-confirmation link (?token_hash=&type=email). Assigns the default applicant role and seeds a client_profiles row on first login, checks super_admin_profiles to override role, and redirects to the correct role dashboard (or to profile completion if required fields are missing).
Auth: None required to call it — it establishes the session from the Supabase code/token itself. Only relative next redirect targets are honored (prevents open-redirect abuse).
Query params: code (OAuth), token_hash + type=email (email confirmation), next (optional relative redirect override).
Response: HTTP redirect (302), never a JSON body.

POST /api/payments/invoice

File: src/app/api/payments/invoice/route.ts
Purpose: Creates a Xendit hosted-checkout invoice for the logged-in user.
Auth: Required — validates supabase.auth.getUser(); returns 401 if not authenticated.

Request body (validated with createInvoiceSchema):

{
  "amount": 300,
  "description": "SRRV application fee",
  "payerEmail": "optional, defaults to the logged-in user's email",
  "successRedirectUrl": "optional",
  "failureRedirectUrl": "optional",
  "paymentMethods": ["optional array of strings"],
  "currency": "optional, 3-letter code",
  "metadata": { "optional": "string map" }
}

Response 200:

{ "success": true, "data": { "id": "...", "invoiceUrl": "...", "externalId": "...", "amount": 300, "status": "PENDING" } }

401: { "success": false, "error": "Unauthorized" }   400: invalid JSON or failed validation   500: Xendit invoice creation failed.

POST /api/webhooks/xendit

File: src/app/api/webhooks/xendit/route.ts
Purpose: Receives payment status callbacks from Xendit and updates the matching payments row. Also sends a confirmation email to the admin mailbox when a consultation payment succeeds.
Auth: Shared-secret token, not a user session — the x-callback-token (or Xendit-Webhook-Token) header must match XENDIT_WEBHOOK_TOKEN; returns 401 otherwise. This is the endpoint to register as the webhook URL in the Xendit dashboard.
Safeguards: only updates payments still in pending status (a late EXPIRED/FAILED event can never downgrade an already-success payment); dedups so a duplicate PAID event for the same user+service can't create two successful payments.
Response: always { "received": true } on 200, or 401/400 for auth/parsing failures.

10. Maintenance Guide

Common issues, how to check logs, how to restart services, and backup/restore.

Common Issues and Fixes

See §12 for the full list of known limitations and cleanup items. Highlights relevant to day-to-day maintenance:

  • A fee amount needs to change — ₱50/₱300 fees are hardcoded in source, not admin-configurable. Requires a code change and redeploy (see §3).
  • A payment looks stuck as "pending" — payment status is only ever updated by the Xendit webhook (src/app/api/webhooks/xendit/route.ts). If a payment never transitions, check that Xendit's webhook is actually configured to call /api/webhooks/xendit with the correct XENDIT_WEBHOOK_TOKEN, and check Xendit's own dashboard for the invoice's real status.
  • A refund was issued — there's no in-portal refund action; refunds happen directly in the Xendit console. The portal will only reflect it once the payment is cancelled there.
  • Emails aren't sending — check RESEND_API_KEY is set; if missing, sends are skipped (not retried) and logged as skipped in the email_logs table.

How to Check Logs

SourceWhere

How to "Restart" Services

There are no long-running servers to restart — this is a serverless Next.js app on Vercel.

  • App: trigger a new deployment (push a commit, or Deployments → ⋯ → Redeploy in the Vercel dashboard) — this is the equivalent of a restart.
  • Database: Supabase is a managed Postgres instance; nothing to restart under normal operation. If the project appears paused/inactive (e.g. on a free tier after inactivity), resume it from the Supabase dashboard.

Backup and Restore

Supabase provides automated backups on paid plans (daily backups + optional Point-in-Time Recovery, depending on plan tier). Confirm the actual plan and retention window in the Supabase dashboard → Project Settings → Backups for the production project (ref kpmzzxzbbethfqqrqacd, matching .env.production) — this wasn't verified live during this documentation pass since it requires an interactive dashboard login. A schema-and-data dump of this project already exists at docs/backup2/ as of the dump date, which can serve as a point-in-time reference independent of Supabase's own backup retention.

To restore: Supabase dashboard → Database → Backups → select a backup point → restore. This is a destructive operation on the target project — confirm with the client before triggering one.

For file storage (documents bucket), Supabase Storage backups follow the same project-level backup policy as the database.

12. Known Issues / Limitations

Security Findings (from Reading the Live Database's RLS Policies Directly)

These were found by reading the actual RLS policy SQL in the production database dump (docs/backup2/schema.sql), not by testing the app's UI — the app's own code never exercises these paths, which is exactly why they're easy to miss.
ItemDetailLocation
A user can set their own payment to "success" without payingThe payments table's RLS policies let an authenticated user INSERT/UPDATE/SELECT their own payment row with no restriction on which columns or values — including status. The app's Server Actions and webhook handler never expose this, but nothing in the database stops a user from calling the Supabase client directly to mark their own payment as success, bypassing Xendit entirely. Recommended fix: restrict the UPDATE policy to only the columns a user should legitimately touch (or drop it entirely and let all writes go through the service-role webhook).docs/backup2/schema.sql payments policies; see §5
A disabled admin's RLS access doesn't actually get revokedThe "is this user an admin" RLS check used across most tables never checks admin_profiles.is_active — only row existence. The app's own authorization correctly treats a disabled admin as an applicant, but that's an application-layer check; the database-layer RLS would still grant admin-level access to a disabled admin who retains a valid session. Recommended fix: change the RLS admin-check subqueries to also filter is_active = true.docs/backup2/schema.sql — every table policy
Password logged in plaintextThe password-reset flow logs the new password to the server console via console.log. Should be removed before production traffic.src/actions/auth.ts:284
